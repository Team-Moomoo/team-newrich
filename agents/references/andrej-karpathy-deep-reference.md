# Andrej Karpathy 딥리서치 레퍼런스

`andrej-karpathy.md` 에이전트의 상세 참고 자료. 사례·인용·한국 적용 상세가 필요할 때 읽는다.

---

## Software 2.0 상세

### 핵심 논리

Karpathy는 신경망을 "또 다른 분류기"가 아니라 소프트웨어 제작 패러다임 자체로 본다. 1.0에서 소스코드는 사람이 쓰고 바이너리로 컴파일되지만, 2.0에서는 **(1) 데이터셋 + (2) 모델 아키텍처**가 소스코드, 학습이 컴파일러, 학습된 모델이 바이너리다.

### 핵심 인용

> "Neural networks are not just another classifier… They are Software 2.0."
> — *Software 2.0* (2017)

> "Software development… takes the form of curating… labeled datasets."
> — *Software 2.0*

### 실제 적용 패턴

- Tesla 오토파일럿: 초기에는 C++ 1.0 코드와 일부 신경망 2.0이 공존. 성능 개선 과정에서 신경망이 기능을 흡수하며 1.0 코드가 삭제되는 방향으로 이동.
- 산업 전반: 비전, 음성, 번역, 게임, 데이터베이스 등에서 1.0→2.0 포팅 흐름.
- GitHub가 1.0의 저장소라면, Hugging Face가 2.0의 저장소(모델/가중치 공유).

### 한국 적용

- 고객 문의 분류: 규칙 기반(키워드 매칭)으로 한계 → 라벨링된 데이터로 분류 모델 학습
- 콘텐츠 모더레이션: 금칙어 목록(1.0) → 문맥 이해 모델(2.0)
- 팀 구조 변화: "코드 엔지니어링"만으로는 안 되고, 라벨링/품질관리/데이터 엔지니어링이 핵심 역량

## Software 3.0 & AI-Native Thinking 상세

### 핵심 논리

LLM으로 신경망이 "프로그래머블"해졌고, 프롬프트가 프로그램 역할을 한다. Karpathy는 이를 "새로운 종류의 컴퓨터"로 간주하며 3.0이라는 별도 층위로 부른다.

### 핵심 인용

> "Your prompts are now programs."
> — YC AI Startup School 강연 (2025)

### LLM ≈ OS 비유

LLM이 CPU, 컨텍스트 윈도우가 메모리처럼 작동하고, 앱은 서로 다른 모델 위에서 실행 가능한 형태로 이식된다. "가장 말이 되는 비유는 운영체제."

### 부분 자율성 (Autonomy Slider)

- 완전자율 에이전트보다 "Iron Man 수트" — 인간이 입고 제어하는 형태
- 작은 자동완성 → 리포지토리 단위 변경까지 자율성을 조절
- 인간이 디프를 빠르게 감사하는 제품 설계가 핵심
- "큰 디프는 검증 비용 때문에 쓸모가 떨어진다"

### 에이전트 = 새로운 사용자

사람(GUI)과 컴퓨터(API) 외에, LLM 에이전트가 제3의 소비자. 문서·제품·웹을 에이전트에게 읽기/행동하기 쉬운 형태로 만들어야 한다:
- 마크다운 문서
- 클릭 대신 실행 가능한 명령
- 에이전트 친화 포맷

### 한국 적용

- 스타트업 제품: 관리자 페이지를 마크다운/CLI 기반으로 재설계하면 에이전트 자동화 가능
- 사내 문서: 위키/노션 → 마크다운 파일 기반으로 전환 시 LLM 활용도 급상승
- "왜 내가 이 클릭-워크플로를 하고 있지?" — 반복 작업을 에이전트가 대신할 수 있는지 점검

## 바이브 코딩 상세

### 핵심 논리

자연어로 개발 의도를 전달하고, LLM/코딩 에이전트의 출력을 반복적으로 수용·수정하며 "코드가 존재한다는 감각"을 약화시키는 프로그래밍 방식.

### 핵심 인용

> 바이브 코딩의 본질: 문법 정확성보다 **의도 전달→실행→관찰→재지시**의 루프가 주요 제어면이 된다.

### MenuGen 사례

- 사진으로 찍은 메뉴를 OCR→항목별 이미지 생성으로 보여주는 서비스
- 코드 생성은 빨랐지만, 실사용 서비스까지의 마찰:
  - 여러 SaaS/배포 스택의 복잡성
  - 인증/결제/도메인/운영 문제
  - LLM 친화적 인터페이스의 필요
- 교훈: "데모→실서비스" 구간이 진짜 병목

### iOS 앱 사례

Swift에 익숙하지 않음에도 주말에 기본적인 iOS 앱을 만듦 — 자연어 기반 개발이 진입장벽을 낮춤.

### 적용 가이드

- **저위험 영역**: 프로토타입, 내부 도구, 실험 — 바이브 코딩 적극 활용
- **고위험 영역**: 결제, 인증, 의료, 법률 — 검증/보안/신뢰성이 코드 생성보다 중요
- **팀 정책**: "바이브 코딩을 어디까지 허용할지" 경계를 명시적으로 설정

## First Principles Learning 상세

### 핵심 논리

추상화가 새는 지점(leaky abstraction)에서 실전 역량이 갈린다. 블랙박스를 사용하기 전에 핵심을 직접 구현해야 디버깅/설계 판단이 가능하다.

### 핵심 인용

> "Backpropagation… is a leaky abstraction."
> — *Yes you should understand backprop*

> "Everything else is just efficiency."
> — *microgpt*

### 미니 구현 시리즈

| 프로젝트 | 목적 | 특징 |
|----------|------|------|
| micrograd | 스칼라 오토그라드 엔진 | 역전파/계산그래프를 직접 손으로 만지는 경험 |
| minGPT | GPT 구조 이해 | 교육과 해석가능성 중심, 읽기 쉬운 코드 |
| nanoGPT | GPT 실전 학습 | 더 실전적 성능/효율("teeth") |
| microgpt | GPT 학습/추론 압축 | 200줄 단일 파일, 핵심 알고리즘만 |

### 분리 원칙

- "핵심 알고리즘 내용"과 "효율(속도/분산/메모리)"을 구획해 사고
- 무엇이 본질이고 무엇이 엔지니어링 최적화인지 구분
- 동일 아이디어를 단계적으로 확장 (교육용 → 실전용)

## Technical Taste (A Recipe for Training Neural Networks) 상세

### 핵심 논리

"학습은 조용히 실패한다" — 코드가 에러 없이 돌아가도 성능이 나쁜 채로 학습이 진행될 수 있다.

### 핵심 인용

> "Fast and furious… only leads to suffering."
> — *A Recipe for Training Neural Networks* (2019)

> "Don't be a hero."
> — *A Recipe for Training Neural Networks*

### 5단계 레시피

1. **데이터와 한 몸 되기**: 모델 전에 데이터 분포/오염/편향/라벨 오류를 눈으로 대량 점검. 이상치가 버그를 드러낸다.
2. **엔드투엔드 스켈레톤 + 멍청한 베이스라인**: 복잡한 모델 전에 단순 모델로 학습/평가 파이프라인의 정합성을 "신뢰할 수 있게" 만들기.
3. **한 배치 오버핏**: 극단적으로 작은 데이터에 완벽히 맞추지 못하면 어딘가에 버그가 있다.
4. **점진적 복잡화**: 입력 신호/기법을 한꺼번에 넣지 않고, 기대한 만큼의 개선이 나는지 검증하며 단계적 추가.
5. **시각화·방어적 점검·집요함**: 조용한 실패를 잡기 위한 지속적 모니터링.

### 스케일링 법칙 관점

"모델 1개"가 아니라 "모델 패밀리" 최적화 문제로 사고. "컴퓨트라는 다이얼을 돌리며 단조롭게 좋아지는 패밀리를 만든다" — 큰 학습 런이 투자 대비 성능으로 이어질지에 대한 신뢰를 제공.

## 교육 철학 상세

### 핵심 논리

학습은 "지식 전달"이 아니라 "학습자가 실제로 생성하는 산출물"로 설계한다.

### Eureka Labs

"교사가 코스 재료를 설계하고, AI 조교가 이를 확장/가이드한다" — teacher+AI symbiosis.
- 첫 제품: 학생이 자신의 LLM을 학부 수준에서 학습/훈련해 보는 코스
- '완제품 사용'보다 '만들기'를 교육의 중심에

### Zero to Hero

- 유튜브 강의와 동일한 노트북/코드를 저장소에 고정
- 학습의 흔적 자체를 커리큘럼 구성요소로 취급
- "코스 수강"을 "코드베이스 탐색"으로 전환

### LLM Wiki (2026)

- RAG처럼 매번 검색·조합하기보다, LLM이 지속적으로 업데이트하는 마크다운 위키
- "Obsidian=IDE, LLM=프로그래머, 위키=코드베이스"
- AI-네이티브의 '중간 산출물' 중심 설계

### AI 학습 통제

"AI로 수업을 한다면, 그냥 채팅창에서 '물리학 가르쳐줘'라고 하면 길을 잃는다" — AI가 따라야 할 감사 가능한 중간 산출물(코스/실라버스/프로젝트 진행)을 만들고 그 범위 안에서만 에이전트를 움직이게 해야 한다.

## 공개 지식 생산 & 개인 브랜드 상세

### 패턴

1. **작고 완결된 레퍼런스**: micrograd/minGPT/nanoGPT/microgpt — 특정 주제의 핵심을 최소 코드로 압축. 타인이 복제→변형→재학습하기 쉬운 형태.
2. **강의-저장소 결합**: 유튜브 강의 + 동일 노트북/코드 저장소 → 시간에 따라 콘텐츠가 사라지지 않고 재현 가능한 지식으로 남음.
3. **아이디어 파일로의 이행**: "코드를 배포하기보다 아이디어를 배포하면, 각자의 에이전트가 환경에 맞게 구현한다." 문서 자체가 에이전트에게 복사-붙여넣기 하도록 쓰임.
4. **교육 조직화**: 개인의 공개 강의 → 조직/제품 설계로 확장 (Eureka Labs).

### 한국 적용

- 기술 블로그/유튜브: "강의 콘텐츠 = 검증 가능한 코드 저장소" 형태로 결합
- 교육 사업: 완성품 납품이 아니라 "학습자가 만드는 과정" 자체를 상품화
- 지식 공유: 이력보다 기여의 흔적(코드/글/강의)이 신뢰를 만든다

## 다른 멘토와의 차별점

### vs Naval Ravikant

Naval은 "코드와 미디어는 허가 없는 레버리지" 같은 원칙을 추상적으로 제시. Karpathy는 레버리지의 구현체를 구체 기술(신경망 가중치, 프롬프트-프로그램, 에이전트 워크플로)로 내려와 설명하며, 레버리지가 작동하기 위한 조건(검증 루프, 데이터, 산출물)을 기술적으로 분해.

### vs Tim Ferriss

Ferriss는 시간 가치 기반 아웃소싱/자동화(생산성 설계). Karpathy는 "기존 프로세스를 덜 일하게 만드는 것"보다 "자연어 인터페이스로 누가 생산자가 될 수 있는지가 바뀌는 것"과 제품/인프라의 재설계에 초점.

### vs Charlie Munger

Munger는 멘탈 모델 격자를 다학제로 수집. Karpathy는 특정 시스템을 "최소 구현으로 분해"해 내부 작동을 직접 획득하고, 그 이해를 비유/프레임으로 압축해 공유.

### vs kepano

kepano의 "file over app"은 디지털 산출물의 장기 보존/소유권 중심. Karpathy도 마크다운/LLM 친화 문서를 강조하지만, 목적은 "보존" 자체보다 "에이전트와의 협업 루프를 빠르게 만들고, 아이디어→구현의 마찰을 줄여 생산을 재구성"하는 쪽.
